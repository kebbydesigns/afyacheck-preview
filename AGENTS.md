# Prototype authoring conventions

- Work only in this Eleventy prototype. Do not modify the separate Laravel project.
- Use shared section views under `src/pages/` with canonical content in section JSON files under `src/_data/`. This is the user's approved workflow for all pages. Use index/show pairs for repeating content types; retain dedicated views for distinct layouts. Keep section markup and ordering in the owning views, with explicit or data-derived permalinks preserving public URLs. Reuse layouts and component partials; do not introduce a single whole-site page factory.
- Services use `src/pages/services/index.njk` and `show.njk`, backed by `services.json`. Media & Resources uses index/show pairs per type plus dedicated overview, press-kit and youth-corner views, backed by `mediaResources.json`.
- Programmes and projects share index/show pairs backed by `whatWeDo.json`; campaigns share index/show plus past and registration views backed by `campaigns.json`; participation pathways share index/show backed by `getInvolved.json`. Policies share one show view backed by `policies.json`. About, contact and utility views use `about.json`, `contact.json` and `supportingPages.json`. Homepage content remains in `home.json` and derives featured campaign facts from `campaigns.json`.
- Derive directories, cross-links and shared facts from their canonical records. Use section-card references for cross-section cards and retain only intentional marketing overrides. Do not recreate individual record folders or duplicate reference catalogues. Reporting table, filters and CSV export all use `about.impact.records`.
- Use descriptive section and component classes in templates. Keep Bootstrap layout, spacing, display, sizing and typography utilities out of template markup, including container/row/column classes.
- Compose those styles with Bootstrap `@extend` rules inside nested section/component SCSS. Use Bootstrap's responsive classes outside media queries; Sass cannot extend an outer utility from inside a media query.
- Retain Bootstrap component classes and state/JavaScript hooks where needed, such as buttons, cards, form controls, dropdowns and collapse.
- Use custom declarations only for requirements Bootstrap does not cover, such as brand colours, image crops, calculated sticky offsets and specific content measures.
- In the header, apply this to every property: prefer Bootstrap utilities through `@extend`, component defaults and native variables. Document retained exceptions where Bootstrap has no suitable value or behaviour (logo sizing, minimum tap targets, calculated sticky offsets, viewport-bounded menus and announcement letter spacing). Do not introduce arbitrary replacements or custom interaction-state values.
- Keep styles with their section or component. Add short, meaningful comments for page sections and SCSS blocks.
- Nest section SCSS to mirror the actual HTML hierarchy: container, section/row, column, inner content, then leaf elements. Keep each element's layout in its owning block, following the footer-bottom/footer-legal/list-legal pattern. Keep genuinely shared defaults once at the component root.
- Source every colour from existing variables in `src/assets/css/_variables.scss` or Bootstrap's variables. Do not add new colour variables or hardcode colour values in section/component styles, templates or data. Use existing variables for alpha overlays and gradients too.
- Let Bootstrap generate button backgrounds, borders and interaction states, and derive link hover colours natively. Do not define custom hover-colour tokens. Keep primary, secondary and dark button text white in normal, hover/focus, active and disabled states using Bootstrap's white variable.
- After relevant changes, build the prototype and run the applicable checks in `scripts/`. The template-style check guards this markup convention.
